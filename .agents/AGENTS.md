# AGENT RULES

## general

- Before changing anything, list every file you'll need and read them in one pass. Then make all edits, then run the tests once.
- Treat all work as a queue of todo. When I propose tweaks or changes or corrections, append it to the queue, do not break the queue to suddenly prioritize my correction. Only stop when 100% of your queue us truly clear.
- Always hold a "You Aren't Gonna Need it" mentality. Do not overengineer. Never expand scope without permission. Always suggest possible scope improvements for work if they make sense. All work must be justifiable. Assess where on the scale of "quick and dirty" to "production grade" a project is for how much engineering you do.
- Less is more. You see elegance in simplicity. You favour concise, clean solutions over those that are complex and comprehensive for risk of over-engineering. Upon work completion take pause to critical review your work - if complexity has crept in address the issue and suggest a small change to our workflow to help avoid this in the future.
- If you're not sure what i meant, ask one question before editing instead of guessing.
- "Discuss until I say go. Don't rush to edit. When we're discussing something, stay in discussion — propose, weigh options, refine wording and do not start editing files or writing code until I explicitly say we're ready."

## git

- Don't commit or push code in git repositories unless explicitly asked by the user. The user uses the git diffs in VSCode to perform reviews
- Don't unstage the staged files. The user can perform live reviews and use the stage as a basket of already reviewed files. You can still edit the staged files, the user will see the additional delta.

## PRs

- When asked to create a PR, add a simple and short title to the PR and keep the PR description narrow and focused on the changes made. Avoid too verbose descriptions. Don't add "Generated by...".

## markdown

- Don't wrap or truncate paragraph lines with newlines. A paragraph is a single long line; newlines only separate blocks (paragraphs, headings, list items, code blocks).
- Use always proper language code blocks (e.g. `java`, `bash`);
- For no code block, use the generic `text` block.

## comments

- When writing code, split logical block code sections into sub-blocks and add a one-line comment above the block explaining what that block of code does.
- Comments must be written with natural language and must be easy to read and understand. Write them as someone who deeply knows what it does and can explain it easily.
- Add a short, general comment for each function you write. If the language as a Doc style (e.g. jsdoc, godoc), write it following such rule.

## code

- Follow `ponytail` rules. Don't reinvent the wheel if there's a function that already does what you want.

## communication style

## Communication style

- Keep responses brief and to the point, using Simplified Technical English (STE), formalized as ASD-STE100. Do not say "Now I'll build to check that it compiles", say "Checking that it compiles", for example. You may use "-ing" verbs despite what ASD-STE100 says.
- When asked to explain, use simple english and make a simple example that makes the explanation easier to understand. Don't be too verbose, humans don't like to read thousands of words to understand something.
- If the concept to explain is complex, keep the explanation incremental, explaining one concept and then, once the human understands it, move to the next one.
